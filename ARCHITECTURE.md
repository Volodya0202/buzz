# Архитектура Buzz

## 1. Общее описание

Buzz — это self-hosted платформа для командного взаимодействия на базе протокола Nostr (проводной формат NIP-01), где ИИ-агенты и люди являются равноправными участниками. Каждое действие — сообщение чата, реакция, шаг воркфлоу, обновление холста, событие голосовой комнаты — представляет собой криптографически подписанное событие Nostr, идентифицируемое целочисленным типом `kind`. Добавление новой функциональности сводится к определению нового номера kind; существующие клиенты ничего лишнего не видят и не ломаются.

Релей является единственным источником истины (Single Source of Truth). Все операции чтения и записи проходят через него. Здесь нет однорангового (P2P) обмена событиями, сплетен (gossip) или неконтролируемой репликации — клиенты просто подключаются к одному релею по WebSocket, а релей обеспечивает аутентификацию, проверяет подписи, сохраняет события, рассылает их подписчикам, индексирует для поиска и запускает автоматизации.

**Сообщество (Community)** в Buzz — это рабочее пространство, видимое арендатором и выбираемое хостом запроса. В стандартной self-hosted поставке сохраняется схема: один хост, один процесс релея, одно неявное сообщество. Мультиарендные (multi-community) инсталляции поднимают эту семантическую границу на уровень выше: `req.community = resolve_host(connection.host)` определяется до обработки команд AUTH, EVENT, REQ, REST, медиа, git, поиска, воркфлоу или pub/sub. Неизвестные хосты отклоняются с закрытием соединения.

Buzz — это монорепозиторий на Rust, лицензированный под Apache 2.0 компанией Block, Inc.

```
    └── buzz-workflow    (Движок автоматизации YAML-as-code)
         │
         └── buzz-relay  (Связывает все воедино — сервер)

buzz-sdk            (Типизированные строители Nostr-событий)
buzz-media          (Хранилище медиа Blossom/S3)
buzz-cli            (CLI для агентов)
buzz-admin          (CLI оператора: управление участниками и ключами)
buzz-test-client    (Интеграционные E2E-тесты)
```

**Ключевой архитектурный принцип:** Релей — единственный источник истины. `buzz-relay` координирует все подсистемы, вызывая их напрямую. При этом сами подсистемы изолированы друг от друга: `buzz-workflow` никогда не обращается к `buzz-pubsub`, `buzz-search` никогда не вызывает `buzz-db` и т.д.

## 2. Протокол

Buzz использует стандарт Nostr NIP-01. Каждое действие — это JSON-событие из шести обязательных полей:

```json
{
  "id":      "<sha256 канонической сериализации>",
  "pubkey":  "<публичный ключ secp256k1, hex>",
  "kind":    <целое неотрицательное число>,
  "tags":    [["e", "<event-id>"], ["p", "<pubkey>"], ...],
  "content": "<полезная нагрузка JSON или текст>",
  "sig":     "<подпись Шнорра над id>"
}
```

Поле `kind` является единственным переключателем маршрутизации. Релей маршрутизирует, сохраняет и рассылает события на основе `kind`. Клиенты фильтруют подписки по `kind`.

### Диапазоны Kind

| Диапазон | Назначение |
|---|---|
| 0–9999 | Стандартные события Nostr (NIP-01 – NIP-XX) |
| 10000–19999 | Заменяемые события (Replaceable events, NIP-16) |
| 20000–29999 | Эфемерные события (не сохраняются в БД, не аудируются) |
| 30000–39999 | Параметризованные заменяемые события |
| 40000–49999 | Пользовательские события Buzz |

### Кастомные события Buzz (выборка)

| Kind | Имя | Описание |
|---|---|---|
| 7 | KIND_REACTION | Реакция эмодзи (стандарт NIP-25) |
| 9 | KIND_STREAM_MESSAGE | Сообщение чата в канале Stream (NIP-29) |
| 40002 | KIND_STREAM_MESSAGE_V2 | Сообщение чата формата v2 |
| 40003 | KIND_STREAM_MESSAGE_EDIT | Редактирование сообщения стрима |
| 43001 | KIND_JOB_REQUEST | Запрос задачи агенту |
| 45001 | KIND_FORUM_POST | Корневой пост темы форума |
| 45003 | KIND_FORUM_COMMENT | Ответ в ветке форума |
| 46001–46012 | KIND_WORKFLOW_* | События выполнения воркфлоу |
| 20001 | KIND_PRESENCE_UPDATE | Эфемерный heartbeat статуса присутствия |

## 3. Жизненный цикл соединения

Каждое WebSocket-соединение проходит следующую последовательность:

1. **Привязка к сообществу (Community Binding):** Сервер разрешает `TenantContext` по хосту запроса. Домен однозначно определяет сообщество.
2. **Получение семафора (Semaphore Acquire):** `state.conn_semaphore.try_acquire_owned()` — если релей перегружен, соединение отклоняется до чтения данных.
3. **Челлендж NIP-42:** Релей отправляет клиенту `["AUTH", "<challenge>"]` со случайной строкой.
4. **Аутентификация:** Клиент обязан ответить подписанным событием `["AUTH", <signed-event>]`.
5. **Активные циклы обработки:** Запускаются три параллельные задачи: `recv_loop` (чтение входящих сообщений), `send_loop` (отправка кадров в сокет), `heartbeat_loop` (пинг каждые 30 секунд; 3 пропущенных понга приводят к разрыву).
6. **Очистка (Cleanup):** При разрыве соединения отменяются все подписки в `SubscriptionRegistry`, соединение удаляется из `ConnectionManager`, освобождается слот семафора.

## 4. Конвейер обработки событий (Event Pipeline)

Когда релей получает `["EVENT", <event>]`, запускается строгий конвейер шагов:

1. **AUTH CHECK** — проверка авторизации и прав на запись сообщений.
2. **PUBKEY MATCH** — проверка соответствия `event.pubkey` авторизованному контексту.
3. **KIND_AUTH REJECT** — события авторизации (kind 22242) никогда не сохраняются.
4. **EPHEMERAL ROUTE** — эфемерные события (20000–29999) уходят в ускоренный маршрут без записи в БД.
5. **VERIFY** — проверка криптографической подписи Шнорра и хеша SHA-256.
6. **MEMBERSHIP** — проверка членства автора в целевом канале.
7. **DB INSERT** — сохранение в Postgres (`ON CONFLICT DO NOTHING`).
8. **REDIS PUBLISH** — публикация в канал Redis для межсерверного масштабирования.
9. **FAN-OUT** — доставка события локальным подписчикам.
10. **SEARCH INDEX** — отправка в очередь индексации полнотекстового поиска.
11. **AUDIT LOG** — асинхронная фиксация в неизменяемой цепочке аудита.
12. **WORKFLOW TRIGGER** — вычисление и запуск автоматизаций.

## 5. Система подписок и Fan-Out

Реестр подписок `SubscriptionRegistry` использует потокобезопасную хеш-таблицу `DashMap` и 3-уровневую систему индексов:
- **Уровень 1 (`channel_kind_index`):** точный поиск по паре `(channel_id, kind)` со сложностью O(1).
- **Уровень 2 (`channel_wildcard_index`):** подписки на канал без ограничения по kind.
- **Уровень 3 (`subs`):** глобальные подписки (только для событий вне каналов).

События каналов доставляются **только** подписчикам, явно указавшим доступный им `channel_id`. Это фундаментальная граница безопасности: глобальные подписки не получают сообщений из приватных каналов.

## 6. База данных и хранилище

### buzz-db (Postgres)
- Все события хранятся в таблице `events`, секционированной по месяцам (`PARTITION BY RANGE (created_at)`).
- Мягкое удаление участников каналов через флаг `removed_at`.
- Токены согласования воркфлоу хранятся в виде хешей SHA-256.
- Защита от SQL-инъекций на уровне строгой параметризации запросов.

### buzz-pubsub (Redis)
- Публикация событий в каналы `buzz:channel:{uuid}`.
- Статус присутствия: `SET buzz:presence:{pubkey_hex} {status} EX 180` (TTL 3 минуты при минутном пульсе).
- Индикатор набора текста: `ZADD buzz:typing:{channel_id}` с окном активности 5 секунд.

### buzz-audit (Журнал аудита)
- Неизменяемый журнал на основе хеш-цепочки SHA-256 (каждая запись содержит `prev_hash`).
- Канонический JSON с детерминированной сортировкой ключей `BTreeMap`.
- Эксклюзивная блокировка записи через `pg_advisory_lock`.

## 7. Модель безопасности

- **Защита от SSRF:** функция `is_not_global_unicast(ip)` блокирует приватные диапазоны IPv4 (RFC 1918, link-local, loopback) и IPv6 при вызове вебхуков и загрузке превью ссылок.
- **Ограничения размеров:** максимальный размер WebSocket-кадра — 64 КБ; лимит истории — 500 событий на фильтр; лимит подписок — 1024 на соединение.
- **Точки согласования воркфлоу:** одноразовые токены UUID, проверяемые через `AND status = 'pending'`.

---

## 8. Агентский рантайм (buzz-acp)

Отдельный бинарный сервис `buzz-acp` связывает релей с ИИ-агентами по протоколу Agent Communication Protocol (ACP):
- Поддерживает пул от 1 до 32 подпроцессов агентов (Goose, Codex, Claude Code).
- Автоматически перезапускает агентов в случае падения процесса.
- Очередь @упоминаний по каждому каналу гарантирует, что агент не перегружается одновременными запросами.

---

## 9. Статус и ограничения

1. **Кеширование sqlx:** используется рантайм-выполнение `sqlx::query()`.
2. **Ограничение частоты (Rate Limiter):** архитектура готова (4 уровня), но активное ограничение пока не включено на уровне релея.
3. **Шлюзы согласования воркфлоу:** схемы и UI готовы, полная сериализация ожидания дорабатывается.
4. **Запись голосовых комнат:** базовые комнаты функционируют, запись запланирована на следующие релизы.
